# MCP Phase 3b — Decisions (Tasks: the eval-only spec floor)

Status: **v2 — CONVERGED (all 3 adversaries folded), READY FOR USER REVIEW before any build.** Synthesized from a 4-scout design pass (eval-as-task / daemon-task-store / sse-server-push / mcp-tasks-spec-fidelity, 2026-07-05), grounded in the shipped eval-core (#2217) and the Phase-3 decisions (`2026-07-03-mcp-phase3-decisions.md`). Prereq met: #2217 eval-core lift shipped + deployed. **Not built unsupervised — the design is the overnight deliverable; 3b opens a new network-facing stateful subsystem and gets user eyes first.**

**Attack summary (all folded into the decisions above):**
- **spec-fidelity** (2025-11-25 spec + schema.ts, no mechanism contradiction): 2 omitted MUSTs [D5 failed-task JSON-RPC-error passthrough; D6 isError→failed status], 2 strength corrections [forbidden→-32601 is SHOULD; pollInterval MAY], wire-shape asymmetry, ISO-8601, D3 SECURITY.md document-the-limitation.
- **seam** (both joins REVISE): 1a panic=abort reality (+new files to `DAEMON_REQUEST_PATH_FILES`); **1b the zombie-task bug** (publish-on-drop `failed` handle); 1d bounded-join → thread the shutdown token now; **2b the freshness-lie** (epoch stamp load-bearing at read, `_meta` staleness); 2c terminal-publication ordering pin.
- **red-team** (2 HIGH + 2 low REQUIREMENTs; entropy + loopback/token/Origin/session posture HOLD): **RT-DOS-2** (blocking `tasks/result` held the OUTERMOST 256-cap permit → re-opened #2218; fixed to an isolated `K≪256` fan-out-capped budget, block-until-terminal preserved); **RT-DOS-3** (allocate-and-abandon → admission-time count cap + total-bytes bound + fixture-read byte cap); RT-LEAK-1 (non-secret thread name, not the taskId); RT-ORACLE-1 (both at-cap conditions → one opaque `Unavailable`). Cross-adversary tension (red-team's 30-60s block-cap vs spec-fidelity's block-until-terminal MUST) resolved in D5 in favor of budget-isolation.

## Headline: 3b is much smaller than forecast, and the spec picks the shape

The spec-fidelity scout (oracle: modelcontextprotocol.io **2025-11-25** Tasks + Progress + schema.ts) established the minimal spec-conformant Tasks floor, and it is a fraction of what the Phase-3 doc's 3b build-list budgeted for. Three of the four "hard" problems evaporate because the features that trigger them are opt-in / MAY:

- **No server-push crux.** The floor has ZERO server-initiated messages (progress is pure-MAY; eval never needs `input_required`; no status notifications). No server-initiated messages ⇒ **no SSE in 3b**. The entire sse-server-push scout's poll-vs-push agony is deferred with P3a-2 — and when progress *is* eventually added, that scout already answered it: transport-side poll-and-emit, daemon stays one-shot.
- **No ownership fork.** `tasks/list` and `tasks/cancel` are independent opt-in capabilities. The spec explicitly says a receiver that cannot identify requestors **SHOULD NOT** declare `tasks.list`. Under our shared-token single-principal model we don't declare either — and the "cancel-one-cancels-all" concern dissolves.
- **No reindex progress/cancel infra.** Progress is MAY, cancel is opt-in, and eval doesn't touch `reindex_files`. The whole 3b-P1/P2/P3 block (reindex progress atomics, decidable-cancel rule, store-side cancel-safety) is out of the floor.

A post-cutoff **2026-07-28 RC** (fetched by the scout, NOT the target) confirms the trajectory: it removes `tasks/list` ("can't be scoped safely without sessions" — exactly our shared-token situation) and moves Tasks to a stateless extension. The floor below is forward-compatible with that direction; the Phase-3 doc's fuller 3b is not. **Re-fetch the RC at build time**; if finalized, target its lifecycle directly (a near-subset of this floor either way).

## What 3b ships (the floor — spec-conformant; MUST vs SHOULD/MAY marked)

Task-augment exactly ONE tool — `cqs_eval` — with `tasks/get` + `tasks/result`. Nothing else. Every item below is either a spec MUST or a deliberately-taken SHOULD/MAY (marked); the floor covers every MUST for the tenant.

## D1 — Task creation is `tools/call` augmentation, NOT a `tasks/create` method

There is no `tasks/create`. A client augments a `tools/call` with a `task: { ttl? }` field in params; the server returns `CreateTaskResult = Result & { task: Task }` immediately instead of the normal `CallToolResult`. **Corrects Phase-3 doc C1** (3a-D4 line 158 names a nonexistent `tasks/create`): the task-store cap is enforced on the augmented `tools/call` itself — reject the augmentation with a JSON-RPC error (spec assigns no dedicated code; use the existing retryable `Unavailable`, surfaced at augment time). `Task = { taskId, status, statusMessage?, createdAt, lastUpdatedAt, ttl: number|null, pollInterval? }`.

## D2 — Eval-only, `taskSupport: "optional"`

- `initialize` capability: `tasks: { requests: { tools: { call: {} } } }` — **omit `list` and `cancel`** (not declaring a sub-capability = not implementing it, fully legal).
- `cqs_eval` in `tools/list` gains `execution.taskSupport: "optional"`; every other tool defaults to `forbidden`. A client augmenting a `forbidden` tool → `-32601` (a spec **SHOULD**, not MUST; the MUST-grade `-32601` is only the `required`-tool-not-augmented case, which we don't use).
- `"optional"` (not `"required"`) is load-bearing: it preserves eval-core's shipped one-shot blocking path for task-unaware clients. `"required"` would force a MUST `-32601` on a normal (non-augmented) call — a backward-compat break.
- `pollInterval` (~5000ms) in `tasks/get` is a spec **MAY** we take, so agent clients poll a 20-min eval sanely.

## D3 — Tasks are DAEMON-scoped, not session-scoped (spec-aligned, not a deviation)

The spec scopes `taskId` to the **receiver** ("unique among all tasks controlled by the receiver"), and binds isolation to an authorization context, not `MCP-Session-Id`. So tasks live in the daemon (the single execution authority), NOT the transport session. **Corrects Phase-3 doc C4** (line 242 framed transport-restart survival as a "recorded deviation"): it is the correct, spec-aligned choice. A `cqs mcp --http` front-end bounce 404s the *session* (3a-D1) but does not strand `taskId`s — a re-initialized client keeps resolving them against the same daemon. Ownership is **single-principal, taskId-as-capability** (possession of the crypto-secure taskId is the handle) — the spec's prescribed no-auth-context posture. **Corrects C2**: the ownership model isn't a fork; the spec picks it. **Spec SHOULD (Docs-Lying-Is-P1 makes it mandatory for us):** "receivers SHOULD document this limitation clearly" — the floor's SECURITY.md amendment states that under the shared-token model any token holder possessing a taskId can `tasks/get`/`tasks/result` it (no per-task ACL; isolation rests on taskId entropy + no-log), and that this is the spec-endorsed no-auth-context posture.

## D4 — Single-flight IS the concurrent-task cap; the guard-lifetime handoff

The shipped `EVAL_IN_FLIGHT: AtomicBool` / `EvalSlotGuard` (analysis.rs:197-219) is the eval tenant's 3a-D4 cap: one live eval task, a second augmented call → the retryable `Unavailable` at create time, no entry allocated. No queue (a queue re-opens the N×20-min GPU-hold wound single-flight closed).

**The guard lifetime.** Today the guard is stack-RAII on the synchronous `dispatch_eval` frame. A task run is async and outlives the augmented call, so the guard can't stay on the create-handler stack. Resolution: **`try_acquire` in the augment handler IS the admission** — the handler spawns the worker only if it wins the slot, and **moves the acquired guard into the worker closure**. The guard lives on the worker's stack for the run and releases on the worker's drop. The admission→acquire window is zero because the winning `try_acquire` is itself the guard handed to the worker (no separate peek-then-acquire — SEAM-CONFIRMED sound). A direct (non-task) eval and a task eval share the one `AtomicBool`, so they can't double-book the GPU. **The slot lifecycle is airtight**; the *entry* lifecycle is where the real bug was (below).

**Panic reality — abort, not "daemon continues" (seam 1a).** `Cargo.toml` sets `[profile.release] panic = "abort"`, so `single_flight_releases_after_panic` (analysis.rs:346, `catch_unwind`) only ever runs under the test profile's forced unwind. In the deployed daemon a panicking eval worker **aborts the whole process** (systemd restarts it; the in-memory TaskStore and every taskId are lost). This is the SAME failure mode as today's synchronous `dispatch_eval` (also aborts on panic) — **no regression** — but the safety argument is not "the guard releases on unwind"; it is the panic-token fence (`daemon_request_path_has_no_production_panic_tokens`, socket.rs:652). The codebase already removed a `catch_unwind` that falsely claimed "daemon continues" (socket.rs:289-296); this doc must not re-commit that documented sin. **BUILD REQUIREMENT:** add the new TaskStore + eval-worker files to `DAEMON_REQUEST_PATH_FILES` (socket.rs:562-571, a hardcoded list — new files aren't covered otherwise). Note `eval/runner.rs` is NOT in the fence today; the 20-min worker inherits that pre-existing gap (file it separately).

**The zombie-task bug the design introduced (seam 1b — the load-bearing fix).** GC's predicate sweeps `terminal_at + ttl < now`, so a worker that dies WITHOUT publishing a terminal state leaves the task at `working` **forever**: never swept, permanently consuming the retained-count cap, and `tasks/result` (spec-MUST block until terminal) polls it until the transport budget kills the block with a lie. Reachable in release via **`thread::Builder::spawn` failure after the entry is inserted** — the dropped closure releases the guard, but nobody touches the entry. Fix: **the worker closure owns a publish-on-drop handle to its `TaskEntry`; `Drop` without an explicit terminal publish writes `failed`.** This covers spawn-failure, early-return, and any future unwind-flip in one construct. **Pin the ordering:** insert the entry, THEN spawn — and if spawn fails, the just-dropped closure's `Drop` marks the orphan `failed` (so even the insert-before-spawn-fail window self-heals). Without this, D6's retained-count cap has no failure-path relief.

**Bounded-join vs the deferred cancel (seam 1d).** The `spawn_hnsw_rebuild` template's 30s shutdown-join is usually real because that worker checks its shutdown flag before each sidecar save; **`eval_core` has no cooperative checkpoint** (D7 defers cancel; runner.rs:315-324 is telemetry-only), so a 20-min eval's bounded join is a guaranteed timeout+detach — pure shutdown latency buying nothing. Resolution: **thread the shutdown `AtomicBool` as the FIRST `Option` cancel side-channel on `EvalCoreParams` NOW**, checked once per query (runner.rs:267) — daemon shutdown then bails the worker within one query (~tens of ms) instead of detaching a 20-min thread that keeps the process alive against systemd's stop timeout. This is plumbing-first: the *same* token the later user-facing `tasks/cancel` lane reuses (D7), introduced in the floor purely for clean daemon shutdown. (The floor still does NOT expose `tasks/cancel`; the token is shutdown-only until that lane lands.)

## D5 — `tasks/get` non-blocking poll; `tasks/result` transport-side poll loop

Both must stay OFF the daemon handler-pool (cap 16-64), or a blocked handler self-DoSes every consumer (the confirmed #2218 finding: at N waiters the pool saturates and CLI search / serve / other MCP get busy-rejected).

- **`tasks/get`**: a cheap one-shot daemon dial — lock the task map (microseconds), clone the `Arc<TaskEntry>`, drop the lock, read atomics + terminal slot, return. Never blocks.
- **`tasks/result`**: the spec MUSTs it block until terminal (~20 min for a large eval). The **transport** owns that block as a poll loop over `tasks/get` — each poll is a sub-ms daemon dial that releases its *daemon* slot immediately between polls, so the daemon pool is never pinned. **The transport-cap fix (RT-DOS-2 — the design's original "separate budget" was ineffective and re-opened #2218):** `enforce_concurrency_cap` (http.rs:301) is the OUTERMOST layer — it `try_acquire`s one of 256 permits (limits.rs:661) and HOLDS it across the entire `next.run` (http.rs:413), BEFORE the body is parsed, so it can't see the JSON-RPC method. A blocking `tasks/result` therefore still consumes a one-shot permit for the full ~20 min, and an ADDITIVE second semaphore does not release it — 256 concurrent blocks 503 every other consumer (fresh `initialize`, `tools/list`, a search `tools/call`, another agent's `tasks/get`). Grounded: `concurrency_cap_permit_released_after_response` + `concurrency_cap_saturated_503s_before_auth` (both green). **REQUIRED:** (a) a blocking `tasks/result` MUST NOT hold an outermost one-shot permit for the block — dispatch method-first and release the outermost permit before entering the poll loop (re-acquire per sub-poll dial), OR exempt the blocking method from the outermost layer and gate it SOLELY on a dedicated blocking budget; (b) that blocking budget is a small `K ≪ 256`, **fan-out-capped per taskId** (one client can mount ≤1–2 blocks on the single running task), so blocking calls can never starve the permits one-shot calls need. **Agents SHOULD prefer `tasks/get` polling** (cheap, non-blocking, `pollInterval`-guided); `tasks/result` blocking is offered for spec-conformance, not as the hot path. **Tension resolved (red-team (c) vs spec-fidelity):** red-team's (c) "bound each block to 30–60s then return poll-again" would violate the spec MUST (`tasks/result` MUST block until terminal, per spec-fidelity). Rejected in favor of budget-isolation: the block runs to terminal but on the isolated tiny `K`-budget, never the 256 one-shot budget — spec-conformant AND non-exhausting. Entirely inside http.rs; no daemon protocol change. On terminal, `tasks/result` returns the underlying result verbatim + `_meta["io.modelcontextprotocol/related-task"] = { taskId }` (MUST). **Two terminal shapes (both MUST):** a succeeded call returns its `CallToolResult` (even one with `isError: true` — that is a *successful* JSON-RPC response carrying a tool-level error); a call that produced a JSON-RPC *error* returns **that same JSON-RPC error**, not a `CallToolResult`. For eval this matters: `eval_core` returning `Err` surfaces today as a JSON-RPC error (the redacted opaque error at analysis.rs:225-231), so a `failed` eval task's `tasks/result` returns that JSON-RPC error — the build must not wrap it in a synthetic `CallToolResult`.

**The daemon socket stays strictly one-request-one-response.** Three new one-shot verbs only (augmented-call handling, `task-get`, and the terminal `task-result` read); socket.rs/daemon.rs untouched. That one-shot invariant is the most load-bearing property in the daemon (every test, the panic-free guard socket.rs:651, the CLI==daemon parity suite rest on it), and the floor preserves it by construction.

## D6 — The daemon TaskStore

`Arc<TaskStore>` constructed in `cmd_watch` (beside the existing shared handles at mod.rs:1373-1403), `Arc::clone`d into `spawn_daemon_thread`, adopted into `BatchContext` (new `adopt_task_store`, mirroring daemon.rs:138-149), snapshotted into `BatchView` at checkout — reachable by the `task-*` handlers via the view (cmd_watch-owned now so the forward-declared reindex tenant can reach it from the watch loop too; the No-Debt-in-Foundation call).

- Internals: `Mutex<HashMap<TaskId, Arc<TaskEntry>>>` held only for microsecond map ops (insert/get-clone/retain); per-entry state on `Arc<TaskEntry>` behind its own sync (an `AtomicU8` status for lock-free `tasks/get`, a write-once `Mutex<Option<TerminalResult>>` the worker fills). The outer BatchContext mutex is touched only at checkout; the map lock never spans a job; the worker touches only its entry + its own `BatchView` snapshot.
- **Terminal publication ORDER is pinned (seam 2c — a real interleaving trap):** the worker fills the result `Mutex` FIRST, then `status.store(terminal, Release)`; readers `status.load(Acquire)` before reading the result slot. Otherwise the D5 poll loop can observe `completed` via `tasks/get`, dial `tasks/result`, and find `None` — an impossible-per-spec terminal-with-no-result manufactured at the join of two individually-correct primitives. `tasks/result` MUST treat "terminal status + empty slot" as **retry-not-error** (belt-and-suspenders against a torn read). The "lock-free `tasks/get`" phrasing invites trusting the atomic alone — that is the trap; the ordering is the fix.
- Runner = `spawn_hnsw_rebuild` template (rebuild.rs:376-520): retained `JoinHandle`, mpsc send-may-fail tolerance (a dropped client never panics the job). **Thread name uses a NON-SECRET id, NEVER the taskId (RT-LEAK-1):** the taskId is a capability handle; `cqs-task-eval-{taskId}` would leak it into `/proc/<pid>/task/<tid>/comm`, `ps -T`, and perf/crash traces, contradicting the "never log the taskId" posture (D3). Name it with a monotonic non-secret job counter or the invalidation epoch (`cqs-task-eval-{seq}`) — the template already names threads with a `&'static` context, not a secret (rebuild.rs:392). No task-lifecycle tracing field emits the raw taskId either. Two inversions vs the template: (a) delivery is **publish-into-`Arc<TaskEntry>`**, not an mpsc a handler recvs (the D5 self-DoS); (b) the `EvalSlotGuard` is acquired at augment-time and moved into the worker (D4). Plus the **publish-on-drop `failed` handle** (D4/seam-1b) so a worker that dies without publishing can't leave a zombie `working` entry.
- Result: the worker drops the completed `EvalOutput` (already `Serialize`, self-contained) into the entry as `serde_json::Value` — the exact conversion dispatch_eval does synchronously today (analysis.rs:312-313). `tasks/result` reads it back.
- **The freshness-lie fix — the epoch stamp is LOAD-BEARING AT READ, not recorded-and-ignored (seam 2a+2b, the sharpest finding).** The worker stamps the entry with the `invalidation_epoch` it ran against (context.rs:769-774). Synchronously today, compute-to-read is milliseconds and `EvalOutput.freshness = fresh` / `index_substrate = resident` is honest. As a 20-min task it is not: a merge landing mid-run bumps the epoch and publishes a new index, and up to `ttl` later `tasks/result` would hand the recall-gate — the ONE consumer that gates ship decisions on R@K — a `fresh`/`resident` verdict describing an index **that no longer exists**. Verbatim return is a spec MUST for result *content*, so the fix rides `_meta` (the spec-sanctioned extension channel, so verbatim-MUST is preserved and the #2217 one-shot parity is untouched): **on terminal read, compare the stamped epoch to the live `invalidation_epoch`; on mismatch inject `_meta.stale_origins`-family markers** (`computed_at_epoch`, `index_moved_since_run: true`). This makes the borrowed "epoch guard" phrase actually guard something — without a reader it was a marker that lies by omission. The recall-gate skill (already substrate-pinning per #2217) reads this marker and refuses a moved-index result.
- Lifecycle: `working` (spec MUST initial state — the name is `working`, not `in_progress`) → `completed | failed | cancelled`; terminal is frozen (MUST NOT transition). `working → completed/failed` directly is legal; `input_required` never occurs for eval. **isError → failed mapping (MUST):** a `CallToolResult` with `isError: true` maps the task to `failed` status — so an eval that surfaces a tool-level error marks the task `failed` even though `tasks/result` returns it as a successful JSON-RPC response (distinct from the JSON-RPC-error path in D5). `createdAt` + `lastUpdatedAt` on ALL task responses (MUST), as **ISO-8601 / RFC3339 strings** (NOT epoch ms); `ttl` (number OR **null**=unlimited) present in `tasks/get` (MUST); `pollInterval` ~5000ms (MAY).
- **Wire-shape asymmetry (build must not mirror-copy):** `CreateTaskResult` NESTS the task — `Result & { task: Task }`; `GetTaskResult` is FLAT — `Result & Task` (task fields at top level), as is `CancelTaskResult`. Don't build one from the other by wrapping/unwrapping blindly.
- `related-task` `_meta` is a MUST on `tasks/result` and on task-related notifications; on `CreateTaskResult` the spec is ambiguous (the normative "all task-related messages" sentence covers it, but the spec's own example omits it and the SHOULD-NOT-exclusion list names only get/list/cancel) — **include it on `CreateTaskResult` too** (cheap; the inclusive reading is safe) and match the reference SDK at build time.
- Task-gone (unknown/expired/GC'd taskId) → JSON-RPC **`-32602`**, never HTTP 404 (404 is session-expiry only). The TaskStore lookup return type encodes `Gone` distinct from any transport 404.
- **Cap = ADMISSION-ENFORCED retained count + a total-bytes bound (RT-DOS-3 — single-flight does NOT bound retention).** Single-flight caps *running* to 1, but a tiny fixture (`{"queries":[]}`) completes in ms, so augment→complete→augment cycles thousands/min, each leaving a terminal entry holding a full `EvalOutput` until `ttl` — piling unbounded between GC sweeps. **REQUIRED:** (a) check the retained-count cap at augment-ADMISSION, BEFORE the worker spawns and BEFORE any entry is inserted; at the cap the augmented call rejects with the opaque retryable `Unavailable` and allocates nothing. Do NOT rely on the 60s GC to enforce the cap — it is `try_lock`-skippable and 60s is a large accumulation window. (b) A TOTAL retained-bytes ceiling accompanies the count cap (count alone doesn't bound memory: 64 × a large `EvalOutput` = GBs). (c) **Bound the fixture read** — `read_fixture_within_root` → `read_to_string` (analysis.rs:243) has NO size cap today; add a byte cap so an attacker-controlled fixture can't be arbitrarily large. Named values: retained count 16–64, total-bytes ceiling tens of MB, fixture cap in the MB range. The Phase-3 "attachments-per-job" clause is index-coalescing — irrelevant to a 1:1 single-flight eval (**corrects C6**).
- **Both at-cap conditions collapse to ONE opaque `Unavailable` (RT-ORACLE-1).** Single-flight-busy (another eval running) and retained-cap-full (store saturated) MUST return byte-identical error envelopes (same code + same message), mirroring `eval_fixture_rejected`'s one-opaque-error-for-two-conditions pattern (analysis.rs:225-231) — else the reject is a store-state oracle distinguishing "eval running now" from "store full of terminal results."
- GC piggybacks the existing 60s accept-loop sweep (daemon.rs:205-210): add `task_store.sweep_expired()` (own `try_lock` + `retain` dropping `terminal_at + ttl < now`) — a memory-reclaim BACKSTOP, NOT the cap enforcer (admission is, per RT-DOS-3(a)). No new timer.
- taskId: crypto-secure, enough entropy to resist guessing (Security MUST under a shared token) — reuse serve's `AuthToken`-grade RNG; short TTL default.

## D7 — What 3b explicitly does NOT ship (each parked with spec justification)

- **SSE / P3a-2** — no server-initiated messages in the floor. Rejoins whenever progress notifications are added. When it does: transport-side poll-and-emit (daemon stays one-shot), per-session monotone event-id counter + bounded replay ring in the transport `SessionStore`, disconnect-is-not-cancellation (the poller is disposable, the job detached). All specced in the sse-server-push brief; none built now.
- **`notifications/progress`** — pure MAY. Eval HAS the checkpoint (runner.rs:315-324) so this is cheap to add later. **Denominator wart to fix when added:** `done = hits.len() + skipped` (runner.rs:319) omits `--category`-filtered queries, so `done/total` caps below 1.0 forever under a category filter; use `idx + 1` (monotonic, reaches total) as the progress numerator. Noted now so the later lane doesn't rediscover it.
- **`tasks/cancel`** — opt-in; eval's cancel would be detach-only anyway (no cooperative checkpoint threaded through `eval_core` yet). A cooperative cancel token through the query loop is a separate later lane. When added, a cancelled eval returns **no consumable result** (or a `partial: true` marker the recall-gate MUST refuse) — never let a truncated R@K read as complete (the category-ordered fixtures make an early cut a different statistic, the 5-25pp-shift trap).
- **`tasks/list`** — spec SHOULD-NOT under a shared token; the RC removes it. Never build.
- **index/reindex as a task** — no consumer need (agents get done/not-done from wait_fresh); no pre-existing progress/cancel infra. Only if a real consumer appears.

## eval_core signature — untouched

Progress + cancel, if/when added, are `Option`-typed side-channels on `EvalCoreParams` (the non-serde adapter bundle, runner.rs:119-134) — a `None`-defaulted progress `Sender` and cancel `Arc<AtomicBool>`. No `eval_core` signature change, no caller churn, and the #2217 parity test holds by construction (side-channels never touch `EvalOutput`; the empty-fixture parity case short-circuits before the loop). For the FLOOR (no progress, no cancel) even these aren't needed yet — the task worker just calls the existing `eval_core` and publishes the terminal result.

## Open questions — RESOLVED by the attack

All five design-time open questions were answered by the three adversaries (see the Attack summary at the top): the `tasks/result` exhaustion (RT-DOS-2, fixed), the guard handoff / panic-release (seam-1a/1b, reframed to the abort reality + publish-on-drop), allocate-and-abandon (RT-DOS-3, admission cap), spec drift (spec-fidelity, 5 corrections folded), and the TaskStore/epoch seam (seam-2a/2b/2c, the freshness-lie fix + ordering pin). The design is converged; the remaining decisions are the build lanes' to execute against this contract.
