# P3a-2 — SSE server-push + progress notifications (decisions)

Status: **v2 — CONVERGED (5 reviewers folded: 2× spec-fidelity, 2× trust-boundary, 1× seam), READY FOR USER REVIEW before any build.** v1 grounded in the inv-p3a2-sse scout brief (direct reads of http.rs / lifecycle.rs / bridge.rs / tasks/{mod,runner}.rs / analysis.rs / eval/runner.rs + vendored axum 0.8.9) and the MCP **2025-11-25** spec (Transports + Progress + Tasks, fetched 2026-07-05). Build waits for lane-3b2 (`feat/3b-2-transport-tasks`) to land — same file, http.rs. **Not built unsupervised — network-facing new stateful surface; gets user eyes first.**

## The convergence (what the attack changed): SHRINK the surface

Three independent findings — a DoS, a spec MUST violation, and a forward-compat stranding — **all resolve to one simplification**: drop the event-id / replay-ring / `Last-Event-ID` resumability machinery entirely. It was imported from generic SSE into a stream whose only payload makes it redundant.

1. **The payload is a monotone snapshot, not a delta stream.** Progress is `{done, total, status}` — any later frame subsumes every missed intermediate. So "replay the gap" and "on reconnect, emit a current-state snapshot" are the SAME recovery for a monotone value; the ring adds nothing a snapshot doesn't already give.
2. **The ring re-opened the #2218 self-DoS one layer up (RT-DOS-4).** "Accrue while no connection is attached" requires a *per-session background poller* decoupled from the 16-stream budget → up to `MAX_SESSIONS`(4096) background pollers each dialing the daemon `task-get` ~1/s, plus 4096 × 64 KiB ≈ 256 MiB attacker-controlled ring memory, `touch()`-per-background-emit defeating idle-TTL. Deleting the ring deletes the whole surface.
3. **The 2026-07-28 RC deletes this machinery by name** (SEP-2567/2575/2663): removes protocol sessions + `Mcp-Session-Id`, removes the GET SSE endpoint (→ `subscriptions/listen`), **removes SSE resumability + `Last-Event-ID` + event ids**, moves Tasks to an extension replacing blocking `tasks/result` with polling. Resumability is a **MAY** even in 2025-11-25, so a no-ids/no-ring variant is equally conformant, much smaller, and doesn't invest in scheduled-for-removal machinery.

**The shrunk floor:** every GET opens a **fresh** stream (no ids, no ring, no `Last-Event-ID` replay). Reconnect recovery = a current-state snapshot per watched non-terminal task, **gated on a per-token, session-scoped high-water** (emit only a strictly-greater `done`). This is the conformance mechanism for progress-MUST-increase, not an optimization.

## Headline: feasibility CLEAN; the daemon stays one-shot

- `src/cli/mcp/http.rs` is axum 0.8 over tokio; `response::sse` + `KeepAlive` already compiled in (`mcp-http = ["serve"]`). SSE = return `Sse<impl Stream<Item=Event>>` from the GET handler. Zero dependency changes.
- **The load-bearing cap fact (CONFIRMED in code by every reviewer):** `enforce_concurrency_cap` (http.rs:397-416) does `next.run().await` then `drop(permit)` — for an SSE handler `next.run` returns the `Response` (carrying the stream body) BEFORE the body is polled, so the 256-permit drops as the middleware unwinds. SSE streams are **starvation-safe AND invisible to the 256-cap** → they need the dedicated D4 budget.
- The daemon socket stays strictly one-request-one-response: the transport owns the poll loop (`task-get` → diff → emit), per 3b D5. One additive daemon field (D2).

## D1 — Scope: standalone GET stream, notifications only, HTTP-only

- Flip the shipped GET→405 floor to: `Accept: text/event-stream` + a live session + valid Origin + valid protocol-version → SSE stream; else the shipped 405/40x behavior.
- The stream carries **only** `notifications/progress` frames, an **optional** terminal `notifications/tasks/status` frame (D3 F1 fix), and SSE keep-alive comments. Never a server→client JSON-RPC *request*; never a JSON-RPC *response* (we never open POST streams, so the resume carve-out never applies). POST keeps returning single JSON — expressly legal per-request server choice.
- **HTTP-only.** Stdio bridge stays poll-only (`tasks/get`); progress is a receiver-MAY with no cross-transport parity requirement in the spec. Documented divergence, not an incomplete sweep.

## D2 — Daemon-side progress plumbing (PR1) — ONE frame, computed at admission

- `ProgressCounters { done: AtomicU64, total: AtomicU64 }` beside `EvalCoreParams`; new Option side-channel `progress: Option<Arc<ProgressCounters>>` (the sanctioned non-serde None-defaulted channel; #2217 parity holds by construction — the empty-fixture case short-circuits before the loop, and the side-channel never touches `EvalOutput`). Note: `EvalCoreParams` has no `Default`, so every construction site gains a `progress: None` line (mechanical; "no caller churn" was an overstatement — it's a one-line touch at ~4 sites incl. the parity test).
- **Pick ONE frame — do NOT cross them (the mirror-bug both seam reviews caught).** v1 restated the D7 denominator fix but *also* flipped `total` to post-filter, recreating the mismatch in the opposite direction (`done=idx+1` over the full set vs `total`=post-filter count → `109/8` under `--category`, progress >100%). Resolution:
  - `done` = count of post-filter **processed** queries (increment *after* the category `continue`, so a filtered-out query doesn't advance it; count no-gold skips as processed), stored at **iteration end** so `done` means *finished*, not *started*.
  - `total` = M, the post-filter query count, **computed at admission** (the parsed set is already in hand at analysis.rs:410) and stamped into the entry **before** insert — closes the `{done:0,total:0}` window a `task-get` between insert and worker-start would otherwise serve.
  - (Equivalent coherent alternative: `done=idx+1`, `total=N=set.queries.len()`. Either pairing is fine; the crossed pair is the bug.)
  - **Name the frame** so `task-get` progress and `EvalOutput.query_count`(=scored `hits.len()`) don't silently disagree.
- `TaskEntry` gains `progress: Arc<ProgressCounters>`, cloned into the worker's params in `dispatch_eval_task` (beside the lane-1 `cancel` token). `task-get` descriptor extends with **optional `{done,total}`** — additive; lane-3b2 was flagged mid-flight to keep the descriptor additive-friendly and preserve client `_meta`. **Read order pin (seam-coherent-join 2):** the descriptor read must load `status` (Acquire) before the counters, matching the worker's store order (counters, then result-fill, then `status` Release) — so a single `task-get` can never report progress *after* terminal, and the terminal frame carries the final `done` via happens-before.
- **Degraded mode (PR2 against a stale pre-PR1 daemon — this box's normal failure):** a descriptor with no `{done,total}` ⇒ emit **no** progress frames (a keep-alive-only stream, already legal), NEVER a synthesized/constant value (would violate MUST-increase).

## D3 — Stream model: fresh stream per connection, snapshot+high-water recovery

- One SSE stream **per connection** (not a resumable per-session logical stream). Body-scoped poll loop: ~1s `spawn_blocking` `task-get` dial (sub-ms, handler pool never pinned), diff, emit. Bounded by single-flight to **≤1 live task daemon-wide**, so at most one meaningful watch exists at a time — the detached-poller load the ring model feared never arises because there's no detached poller.
- **Emission gate (the conformance core — F1 + Q3):** ALL emissions — live, reconnect-snapshot, terminal — pass a **per-token, session-scoped high-water**: emit a progress frame only when `done` strictly exceeds the last value ever emitted for that `progressToken`. A status-only transition (done unchanged) emits **no** progress frame. This makes progress-MUST-increase hold on the common path (the final-`done` frame and the status-flip frame no longer double-emit) and across reconnect/takeover.
- **Terminal signal (F1 / Q2):** completion is conveyed by `task-get` (the client polls it anyway). **Optionally** emit one `notifications/tasks/status` frame at the terminal transition — 2025-11-25 defines it (a pure MAY, full `Task` object, no monotonicity constraint); when sent it **SHOULD NOT** carry `related-task` `_meta` (taskId is in params). Progress frames only while observed `status == working`.
- **Reconnect = fresh stream:** no `Last-Event-ID`, no replay. On connect, emit a current-state snapshot per watched non-terminal task, gated on the same high-water (so a reconnect can't re-emit an already-seen `done`).
- **Daemon-restart rule (seam Finding 1, HIGH — the two-process trap):** the TaskStore lives in `cqs watch --serve`; the stream lives in the `cqs mcp --http` process. A cqs-watch restart mid-eval (routine on binary updates) evaporates the task; `task-get` then returns `Gone`/`-32602`. `Gone` is neither diffable nor terminal, so without a rule the stream survives on keep-alives **forever**. Pin: a **dial failure** = retry with backoff (transient); an **authoritative `Gone` after a successful dial** = terminal-for-watching → drop the token, close the stream (server MAY close any stream); the client re-syncs via `task-get`, which correctly answers `-32602`. Never fabricate a terminal progress frame.
- **No progressToken on the augmented call → no frames** for that task (spec MUST: only reference provided tokens); the stream may be keep-alive-only. `KeepAlive` ~15s (also the WSL localhost idle-drop mitigation); keep-alive is an SSE comment (structurally carries no id).
- **Watch list:** `(taskId, progressToken)` per session; **prune the entry at terminal** and **bound the list** (a third per-session accumulator otherwise — RT-DOS-6).

## D4 — Stream budget + shutdown (permit HANDOVER, not re-acquire)

- Dedicated `Semaphore(MAX_SSE_STREAMS = 16)` in `HttpState` (const, no env var). The permit lives in `SessionState` (per-session slot), released on connection close / stream end.
- **Takeover HANDS the permit (RT-DOS-5 / seam Finding 4 — the fix that makes per-session=1 structural):** a second GET on a session that already holds a live stream **transfers** the existing permit old→new under the session-state lock; it does **NOT** `try_acquire` a second. Only a *first-stream-for-session* acquires from the semaphore; at-cap → 503. This kills two bugs at once: one session can no longer hold N permits (defeating the 16-budget), and a legitimate reconnect-at-cap no longer 503s itself against its own zombie stream's permit.
- **Graceful shutdown:** tee the shipped `shutdown_signal()` (http.rs:305-324) into a `tokio::sync::watch` sender **before** the future is handed to `axum::serve` (currently it's consumed solely by `with_graceful_shutdown` at http.rs:246, so streams would never see it); every stream `select!`s on it and ends. Test must drive the real signal path, not the watch in isolation.
- **Hygiene pins:** no compression middleware on this router (buffers SSE flush — absent today, pin with a comment); `X-Accel-Buffering: no` on SSE responses; default SSE message type (no custom `event:` — SDK clients listen for the default); `SessionState`/watch-list `Debug` must not render taskIds (RT-LEAK-2 — match the sibling's `TaskId`/`TaskDescriptor` redaction so a crash trace can't dump capability handles).

## D5 — Spec pins that ACTIVATE on the GET/SSE flip (all MUST unless marked)

Verified verbatim against the 2025-11-25 pages by both spec reviewers; these are the ones the flip newly triggers and the doc must carry:

- **Origin (F2):** validate the `Origin` header on the GET connection; present-and-invalid → **403** (DNS-rebinding; the long-lived stream is the juicier target). Carry the shipped Host/loopback posture onto GET.
- **Protocol-version (F7 / OQ6):** the shipped `check_protocol_version` is **POST-only** (http.rs:424; `handle_get`/`handle_delete` skip it). The GET flip MUST run it: present-and-invalid → **400**; absent → fall back to the session-negotiated version (SHOULD assume 2025-03-26 only when there's no other signal). Mirror POST, add a test.
- **Session header (spec Session Mgmt #2 vs #3):** missing `MCP-Session-Id` (other than init) → **400**; terminated/unknown id → **404**. Pin the 400-vs-404 split (v1 said only "404 unknown").
- **`related-task` `_meta` (F-omission):** `io.modelcontextprotocol/related-task = {taskId}` on progress frames is a **spec MUST** (not merely a 3b-doc pin) — add it to the checklist. (The optional `tasks/status` frame is the exception: SHOULD-NOT carry it.)
- **`retry` field (F4):** the GET-close SHOULD applies when a *connection* closes without terminating the *stream*. Takeover/shutdown/expiry all terminate the logical stream for that connection, so `retry` isn't implicated — **state that explicitly** and take the deliberate no-`retry` posture (honoring it on takeover would tell the superseded client to reconnect and take the stream back — a two-client ping-pong).
- **Non-405 GET rejects are spec-legal (F4 — correct the v1 rationale):** "stream-or-405" is only about *not offering SSE at all*; the spec itself layers 403/404/400 onto GET, and the reference TypeScript SDK returns **409** for a second concurrent GET. Takeover is still the choice (rides the explicit "server MAY close any stream," keeps crash-reconnect working) — but it stands on that merit, not on a false "no legal alternative." 503-at-cap is legal-gray (not enumerated, not forbidden; 405 would mis-signal "no SSE here" and a client may permanently stop trying) — keep it, document it as a conscious extension.

## D6 — What P3a-2 does NOT ship

POST-initiated SSE (POST stays single-JSON); server→client JSON-RPC requests; event ids / replay ring / `Last-Event-ID` resumability (**dropped in v2** — redundant + RC-deleted); `tasks/cancel` (separate lane; disconnect SHOULD NOT read as cancel — pinned by disconnect-leaves-job-running); stdio push (D1, documented divergence). The optional `notifications/tasks/status` terminal frame is in-scope but MAY.

## Requirement checklist (build-lane contract)

Budget/DoS: single stream budget (16) both directions (streams-at-cap → one-shot POST still 200; stream survives 256-cap saturation) · permit in SessionState, released on stream end · **takeover TRANSFERS the permit under the session lock, never acquires a second** · shutdown watch (teed from the real signal) ends streams · watch-list pruned at terminal + bounded. Spec: 405 preserved for non-SSE GET · **Origin 403 on GET** · **protocol-version 400-if-invalid on GET** · **400-missing vs 404-unknown session** · no JSON-RPC response frames on the GET stream · **progress `related-task` _meta MUST** · progress **strictly-increasing per token** (high-water gate) · progress stops at terminal (no post-terminal progress frame; terminal via task-get / optional tasks/status) · no-token → no frames · disconnect-leaves-job-running. Correctness: **one progress frame (processed-count vs M), stored at iteration-end, M stamped at admission** · status-before-counters descriptor read · degraded-mode (absent counters ⇒ no frames, never synthesized) · **daemon-restart: authoritative Gone ⇒ close stream, dial-failure ⇒ backoff-retry**. Hygiene: no compression (comment pin) · `X-Accel-Buffering: no` · default SSE message type · `SessionState` Debug redacts taskIds.

## Open questions — RESOLVED by the attack

- **Q1 (takeover vs 409):** takeover, on the crash-reconnect merit + explicit "server MAY close any stream"; with the D4 permit-handover fix (else it fails at cap). Drop the false "409 illegal" premise (the ref SDK uses 409).
- **Q2 (task-status notification):** 2025-11-25 defines `notifications/tasks/status` (MAY); adopt it *only* as the optional terminal completion frame (D3), progress-only otherwise.
- **Q3 (snapshot vs MUST-increase):** per-token session-scoped high-water gate on all emissions — the conformance mechanism, not over-engineering.
- **Q4 (ring bound / over-engineering):** **over-engineered — drop the ring/resumability** (redundant with snapshot + high-water; RC-deleted). This was the biggest single simplification.
- **Q5 (stdio divergence):** spec-clean (progress is receiver-MAY, no parity requirement); house-rule where to document.
- **Q6 (protocol-version on GET):** validate-if-present (400 invalid), tolerate-absent (session-negotiated fallback); mirror POST; the shipped GET skips it today — must add.
